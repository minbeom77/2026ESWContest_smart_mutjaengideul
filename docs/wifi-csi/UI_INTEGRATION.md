# 수어 UI + 최신 노트북 CSI 통합

작성: 2026-10-04 (Asia/Seoul). 실기기 통신 점검 결과는 [ATLAS 검증](ATLAS_VALIDATION.md)에 기록한다.

## 서비스 목적과 메인 화면

청각장애인이 초인종·경보·가전 동작 완료를 알아차릴 수 있도록 화면에 알리는 것이
목표다. Wi-Fi 센싱은 연결된 수신기의 관측 공간에 사람이 있는지 판단하는 보조
입력이다. 행동 분류 결과를 곧바로 집 전체의 재실·부재로 해석하지 않는다.

- 메인 화면: 수신 상태, 현재 모델의 행동 예측·모델 점수, 인식 시작·중지.
- 별도 센싱 화면: 신호 수집·전처리 관찰, 기록 관리, PC 학습, 모델 가져오기.
- 메인은 `/state?view=summary`를 사용해 파형 전처리를 반복하지 않는다. 응답이
  중단되거나 신호가 끊기면 이전 행동을 지운다.
- 현재 걷기·앉기·정지 모델은 재실 판정에 사용하지 않는다. 메인에 미학습 상태를 표시한다.

재실용 실험은 빈 공간, 사람이 가만히 있는 상태, 사람이 움직이는 상태를 다른
회차로 수집하고 독립 회차에서 평가해야 한다. 가만히 있는 재실을 부재로 판단하는
비율과 부재 전환 지연을 함께 측정한다. 복수 공간·집 전체 상태는 센서 배치와
관측 범위를 확인한 뒤 설계한다.

기존 MQTT Topic/JSON은 유지한다. 재실 정보는 알림 위치와 반복
방식을 정하는 데 활용할 수 있지만, 판단 불명이나 부재 예측 때문에 긴급 경보를
숨기지 않는다. 화면·조명·진동 장치의 실제 알림과 사용자 확인 경로는 별도 통합
검증 대상이며, 이 변경에서 새로운 MQTT Topic이나 JSON Key를 추가하지 않는다.

## 생활 지원 기능과 연결 상태

| 기능 | 화면 동작 | 현재 연결 상태 |
| --- | --- | --- |
| 초인종 | 호출 사실을 큰 글씨로 표시하고 사용자가 확인 | 입력 장치와 이벤트 계약 미연동 |
| 재난 | 재난 안내와 센싱 공간의 활동 예측을 함께 표시 | 재난 API 경로 구현, CSI 상태 표시 추가. 실제 경보 수신 시험은 별도 |
| 세탁 완료 | 세탁 완료 사실을 표시하고 사용자가 확인 | LG 기기의 완료 이벤트 수신 경로 미구현 |
| 수어 | 지원하는 수어를 자막으로 표시하고 등록된 명령 전달 | 실제 카메라→MQTT→자막 전달 관찰. 번역 정확도와 가전 실물 작동은 별도 검증 |

초인종·세탁 완료는 저장소에 승인된 Topic/JSON 명세나 수신 코드가 없다. 이름을
임의로 정해 구독하지 않는다. 팀의 기존 명세와 실제 이벤트 발행 장치를 연결한 뒤
수신→화면→확인 처리까지 시험한다. MQTT 연결 성공만으로 이 기능이 연결됐다고
표시하지 않는다. LG 기기의 완료 알림은 Wi-Fi CSI 행동 인식 결과로 대신하지 않는다.

모든 알림은 움직임 유무와 무관하게 표시하는 것이 목표다. 움직임은 상황을 설명하는
보조 정보이며 경보 표시 조건이 아니다. 재난 화면에서 CSI 응답이 중단되어도 안내와
확인 버튼은 유지된다. 현재 모델 예측을 대피 완료나 사용자 안전으로 해석하지 않는다.
조명·진동 등 추가 알림 장치의 실물 동작은 아직 통합하지 않았다.

## 기준과 역할

- UI 기준: 팀 `feature/SW`의 기존 SafeHub Flutter 화면. 기존 수어·가전·알림 흐름을 유지하고 센싱 페이지를 추가한다.
- CSI 기준: 노트북 `WifiSensing2-src`의 현재 소스를 별도 runtime 폴더에 복사한다. 파일별 SHA-256을 기록한다. 기존 EXE와 원본 데이터는 수정하지 않는다.
- 최신 파이프라인: 52개 채널, DWT → 표준화/PCA 1성분 → FFT 저역 통과, 4초/240시점. 같은 함수를 관찰·학습·추론에 재사용한다.
- I/Q 입력은 숫자 배열에서 진폭으로 변환한다. 기존 문자열 변환기와 변경 해시를 보존하고, 표시·학습·추론 입력의 수치 동등성을 검사한다. 전처리 수치와 모델 구조는 유지한다.
- PC: 수집, 기록 선택, 학습, 모델 내보내기. Pi: 수집, 전처리, 추론. Pi 모드에서는 학습 요청을 거부한다.
- 기존 MQTT Topic/JSON을 변경하지 않는다. 이번 로컬 제어 API는 UI와 CSI 프로세스 사이의 통신이며 팀 장치 간 MQTT 규격을 대체하지 않는다.

## 구조

SafeHub Flutter 페이지 → 같은 기기의 loopback HTTP 제어 API → 최신 CSI Python 엔진.
카메라/수어 프로세스는 기존대로 별도로 실행한다. CSI 처리 때문에 카메라나 화면을 블로킹하지 않는다.
UI 종료·페이지 이동은 수집을 종료하지 않는다. 명시적 수집 취소/연결 해제와 프로세스 종료를 구분한다.

## 이번 작업의 검증 범위

장비 없이 synthetic CSI의 수집·전처리 토글·선택 학습·모델 추론 경로를 검증한다. 모의 데이터는 별도 영역에 저장하고 실측 모델과 혼합하지 않는다. 모의 인식 결과를 안전 경보로 발행하지 않는다.
신호가 끊기면 이전 파형/행동을 지우고 대기 상태로 전환한다. USB 재연결 또는 장치 시간 초기화 시 진행 중 수집을 취소한다.
실시간 버퍼는 제한하며, 무제한 원본 저널을 만들지 않는다. 사용자가 요청한 구간만 저장한다.

## 실제 장비 연결 후

사용자가 준비한 연결 장비: 외부 터치디스플레이, 라즈베리파이, 카메라, 스피커. Pi OS와 각 장치의 연결 방식은 실물 연결 시 확인한다.

1. Pi 모델·RAM·64비트 여부·OS(ATLAS/webOS 또는 Raspberry Pi OS)를 확인한다. OS 확인 전 이미지/펌웨어를 덮어쓰지 않는다.
2. 기존 수어 앱을 해당 OS의 도구로 빌드하고 카메라를 확인한다. 현재 pubspec에는 `/opt/flutter-atlas-plugins` 의존성이 있다.
3. C6 RX를 USB로 연결하고 펌웨어 출력과 최신 52채널 입력 호환성을 확인한다.
4. PC에서 내보낸 모델을 Pi에 배포하고 동일 입력의 PC/Pi 전처리·추론 결과를 비교한다.
5. 동시 실행 지연·CPU/RAM·수신 공백·USB 분리/복구·장시간 운전을 측정한다.
6. MQTT 이벤트 이름/우선순위 매핑과 v1.2 승인 상태를 팀과 확인한 후 안전 알림·액추에이터 연결을 활성화한다.
7. 개인 feature 브랜치에서 develop 대상 PR을 제출하고 팀원 검토를 받는다. main 직접 push/merge는 하지 않는다.

합성 테스트 통과는 실측 행동 정확도나 Pi 실기기 성능을 보장하지 않는다.

터치디스플레이에서는 화면 해상도·회전·터치 좌표·스크롤·문자 입력을 확인한다. 카메라는 실제 프레임과 수어 결과의 수신을, 스피커는 선택된 오디오 장치와 TTS 출력·중복 재생 방지를 확인한다. 센싱과 카메라를 동시에 켰을 때의 USB 전력·수신 공백·처리 지연도 측정한다.

## Windows에서 장비 없이 실행

`APP_LOCAL_PREVIEW=true`를 명시한 Windows 체험 빌드는 수어 홈과 센싱 페이지를 유지하면서 MQTT·카메라·재난 API의 자동 연결을 시작하지 않는다. 화면에 체험 모드를 표시하고, 실제 수어·안전 감지는 장비 미연결로 표시한다. 사용자가 센싱 페이지의 모의 신호 버튼을 누를 때만 synthetic CSI를 시작한다.

이 옵션의 기본값은 false이다. 실제 모드에서는 홈의 **연결 설정**에서 서비스 주소를 저장한다. 주소가 없으면 미설정 상태로 대기하고 저장하면 새 주소로 다시 연결한다. CSI는 `--real-only` 서비스에 연결하며 모의 신호를 사용할 수 없다. 자세한 실행 방법은 [실제 모드 안내](REAL_MODE.md)에 있다.

Windows 실행기는 별도 데이터 폴더를 사용하고, 앱 종료 시 자신이 시작한 센싱 서비스도 정리한다. 이 노트북의 Python 환경을 참조하는 로컬 실행본은 다른 PC 또는 Pi용 독립 배포 패키지가 아니다.

구현 후 [검사 결과](UI_INTEGRATION_VALIDATION.md)에 통과 항목과 미검증 범위를 기록했다. Notion 반영과 팀 검토는 후속 작업으로 남아 있다.

## 경보 통합과 자동 음성 자막 (2026-10-04)

현재 Pi 배포본은 [로컬 스트리밍 STT](../../SW/local_stt/README.md)를 사용한다.
서버의 `/health`가 `safehub.pcm.v1`을 제공하면 PCM을 WebSocket으로 연속 전송한다.
아래 WAV 구간 전송 설명은 기존 팀 HTTP 서버를 사용할 때의 호환 경로다.
음성을 외부로 보내지 않으려면 STT 주소를 `http://127.0.0.1:8766`으로 설정한다.

홈 오른쪽의 `경보 · 재난 알림`에서 화면 경보, 최신 재난 내용과 상세 보기를 함께 확인한다.
기존 재난 카드 위치에는 `실시간 음성 자막`을 표시한다. 의사소통 화면도 같은 자막 상태를 공유한다.
실제 모드에서 STT 서버 주소가 설정되어 있으면 앱 시작 시 마이크를 연다. 일시정지와 자막 지우기는 화면에서 직접 조작한다.

마이크는 16 kHz, 16-bit mono PCM 스트림을 유지한다. 음성 구간은 약 2.4초마다 누적 WAV로 기존 `/stt`의 `audio` 필드에 전송하고,
800 ms 침묵 또는 최대 12초 구간에서 마무리한다. 같은 구간의 중간 결과는 덮어써서 반복 표시하지 않는다.
음성 여부는 짧은 프레임의 RMS로 추정하므로 생활 소음이나 작은 목소리에 대한 현장 조정이 필요하다.
이 방식은 기존 파일 기반 API를 이용한 자동 구간 자막이다. 글자 단위 스트리밍은 아니며 구간 길이와 서버 추론 시간만큼 지연된다.

동시에 처리하는 요청은 하나이고 대기는 최대 두 구간으로 제한한다. 밀린 구간은 오래된 것부터 생략한다.
자막은 최근 여덟 구간만 유지하며 클라이언트에 녹음 파일을 저장하지 않는다. 서버 오류 뒤 5초 동안 새 요청을 보류하고 다음 음성에서 재시도한다.
마이크 연결 해제는 상태 메시지와 다시 시작 버튼으로 표시한다. 안전 경보 중에는 자막을 잠시 멈추고 마지막 경보 확인 뒤 재개한다.
MQTT Topic/JSON과 CSI 수집·추론 경로는 변경하지 않는다.

음성 프레임에는 약 20 Hz의 DC 차단 필터를 적용한다. 시작 전 400 ms를 보존하고 짧은 충격음이 단독 구간으로 전송되지 않도록 최소 음성 길이를 300 ms로 둔다. 중간 결과는 임시 자막임을 표시하고 문장 종료 결과로 교체한다. 실제 정확도와 지연은 마이크 배치·잡음·발화에 따라 확인해야 한다.

서버 요청 처리 중에는 새 중간 결과 요청을 대기열에 넣지 않는다. 완료된 문장 요청은 최대 두 개 보존한다. 요청별 음성 길이·대기 시간·응답 시간만 진단 로그에 기록하며 인식 문장은 기록하지 않는다.
